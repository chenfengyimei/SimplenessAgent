# SimplenessAgent 模型接入与评测方案

## 1. 目标

建立统一模型边界，使以下运行方式共用同一 Agent Core：

- 软件托管的本地 llama.cpp。
- 用户已有的本地 vLLM/SGLang/Ollama/LM Studio。
- 局域网模型服务器。
- 云端或企业 OpenAI-compatible API。
- 后续其他协议 Provider。

重点参考和验收模型为 `Qwen3.6-35B-A3B`，但架构不得把模型名、Thinking 格式或 Tool Call 解析硬编码到 Agent Worker。

## 2. 三层抽象

### 2.1 Provider

协议适配器，处理认证、请求格式、流式事件、错误和响应标准化。

首期实现：

- `openai_compatible`
- `mock`

后续可增加：

- `anthropic_compatible`
- `dashscope_native`
- 企业自定义网关

### 2.2 Deployment

实际可调用实例。例如：

- `qwen-local-llamacpp-q4`
- `qwen-local-vllm-fp8`
- `qwen-cloud-api`

Deployment 保存端点、凭据引用、引擎、量化、并发、超时、上下文和能力快照。

### 2.3 Model Profile

描述某个模型在不同 Agent Role 下的行为参数：

- Planner。
- Executor。
- Verifier。
- Memory Curator。
- Summarizer。

## 3. Go 接口草案

```go
type ChatProvider interface {
    Chat(ctx context.Context, req ChatRequest) (ChatResponse, error)
    ChatStream(ctx context.Context, req ChatRequest, sink StreamSink) error
    CountTokens(ctx context.Context, req TokenCountRequest) (TokenCount, error)
    HealthCheck(ctx context.Context) HealthStatus
    ProbeCapabilities(ctx context.Context, req ProbeRequest) CapabilitySnapshot
}

type EmbeddingProvider interface {
    Embed(ctx context.Context, req EmbedRequest) (EmbedResponse, error)
}

type RerankProvider interface {
    Rerank(ctx context.Context, req RerankRequest) (RerankResponse, error)
}
```

Agent Core 只能依赖这些接口和标准对象。

## 4. 标准响应

`ChatResponse` 至少包括：

- `message_id`
- `text`
- `reasoning_summary` 或推理引用
- `tool_calls[]`
- `usage`
- `finish_reason`
- `latency`
- `provider_metadata`
- `raw_response_artifact_id`

Tool Call 标准字段：

- `id`
- `name`
- `arguments_json`
- `sequence`
- `provider_raw_type`

禁止 Tool Runtime 读取 Provider 原始 JSON。

## 5. 错误分类

统一错误码包括：

- `AUTHENTICATION_FAILED`
- `ENDPOINT_UNREACHABLE`
- `RATE_LIMITED`
- `REQUEST_TIMEOUT`
- `REQUEST_CANCELLED`
- `CONTEXT_OVERFLOW`
- `OUTPUT_LIMIT_REACHED`
- `INVALID_RESPONSE`
- `INVALID_TOOL_CALL`
- `CONTENT_REJECTED`
- `MODEL_UNAVAILABLE`
- `CAPABILITY_UNSUPPORTED`
- `PROVIDER_INTERNAL_ERROR`

每个错误声明：是否可重试、建议等待时间、是否需要缩小上下文、是否允许换 Deployment。

## 6. 能力探测

### 6.1 探测原因

模型名称、API 兼容声明和真实 Agent 能力可能不一致，尤其会受 Runtime、Chat Template、Tool Parser 和量化影响。

### 6.2 探测项目

| 能力 | 探测方法 |
|---|---|
| 文本 | 固定短问题和精确预期格式 |
| 流式 | 检查增量事件和最终聚合一致性 |
| 单工具 | 要求调用一个无副作用工具 |
| 参数 Schema | 多字段、枚举、必填和嵌套对象 |
| 工具结果回传 | 两轮模型—工具—模型闭环 |
| 连续工具 | 同一任务两次顺序 Tool Call |
| 并行工具 | 可选测试，不支持则关闭能力 |
| Thinking | 检查开关、字段和最终文本 |
| Preserve Thinking | 检查历史推理上下文兼容性 |
| Token Count | 与实际请求用量做误差比较 |
| Context | 阶梯增加输入直到安全上限 |
| Cancel | 中途取消并确认连接释放 |
| Vision | 可选固定图片测试 |

### 6.3 能力快照

```json
{
  "supports_tools": true,
  "supports_parallel_tools": false,
  "supports_thinking": true,
  "supports_preserve_thinking": false,
  "supports_vision": true,
  "supports_token_count": false,
  "reliable_context_tokens": 65536,
  "tool_schema_pass_rate": 0.98,
  "probed_at": "2026-08-11T00:00:00Z"
}
```

能力快照有过期时间。Runtime、模型、模板或参数变化后必须重新探测。

## 7. Qwen3.6-35B-A3B Profile

初期 Profile 采用官方推荐参数作为起点，再以本项目 Golden Tasks 调整。需要分别建立：

### Planner Profile

- Thinking 开启。
- 较低或适中的温度。
- 只读工具或无工具。
- 强制 Plan Schema。
- 较大的输出预算。

### Executor Profile

- 优先 Non-thinking 或有限 Thinking。
- 较低温度。
- 小工具集合。
- 单 Tool Call 模式作为可靠基线。
- 严格停止条件。

### Verifier Profile

- Thinking 开启。
- 只读。
- 必须引用 Evidence。
- 不能仅复述 Executor 结论。

### Memory Curator Profile

- 后台低优先级。
- 结构化候选记忆输出。
- 不具有执行工具权限。

Profile 参数必须纳入评测指纹，不能只记录模型名称。

## 8. 本地 Runtime 管理

### 8.1 默认策略

第一桌面版本优先管理 llama.cpp Server，原因是跨平台、可分发和 GGUF 量化生态。

### 8.2 高性能策略

vLLM/SGLang 作为已有端点或安装向导接入。首期不把 Python/CUDA/WSL 全部打入主安装包。

### 8.3 Runtime Manifest

包含：

- Runtime 名称和版本。
- OS/Arch/GPU Backend。
- 下载地址和 SHA-256。
- 可执行文件。
- 支持的参数。
- 许可证。
- 兼容模型家族。

### 8.4 Model Manifest

包含：

- 模型 ID、Revision、格式和量化。
- 文件列表、大小和哈希。
- 最低/推荐内存显存。
- 模态和上下文。
- 推荐 Runtime 参数。
- 来源与许可证。

## 9. 路由与故障转移

### 普通任务

可配置：

- 固定 Deployment。
- 主 Deployment + 备用 Deployment。
- Planner 与 Executor 使用不同 Deployment。

发生切换时：

- 记录路由事件。
- 重新编译兼容上下文。
- 显示给用户。
- 不把不同 Deployment 的指标混为一次模型结果。

### 评测任务

- 固定 Deployment。
- 禁止静默切换。
- 失败作为该 Deployment 的真实结果。

## 10. Deployment Fingerprint

每次运行保存：

- Provider 名称和版本。
- 模型名称与 Revision。
- 本地/远程。
- Runtime 和版本。
- 量化方式。
- Chat Template 哈希。
- Tool Parser 和 Reasoning Parser。
- Model Profile 版本。
- Sampling 参数。
- Context 和输出上限。
- 硬件摘要。
- 能力快照 ID。

API Key、完整 Base URL 查询参数和敏感请求头不得写入指纹。

## 11. Golden Task 体系

### 11.1 Case 结构

- 初始 Workspace Fixture。
- 用户目标和约束。
- 权限策略。
- 最大预算。
- 允许的非确定性范围。
- 预期 Artifact。
- 必须满足和不得发生的断言。
- 评分规则。

### 11.2 首批分类

- 指令遵循。
- 结构化 Plan。
- Tool Call Schema。
- 文件读取和搜索。
- 单文件安全修改。
- 多文件修改。
- 测试驱动修复。
- 命令超时和继续等待。
- 上下文溢出与压缩。
- 记忆召回。
- 恶意 Prompt/工具输出注入。
- 危险操作审批。
- 崩溃恢复。
- 子 Agent Handoff。

## 12. 评测指标

### 结果指标

- Task 完成率。
- Acceptance Criteria 通过率。
- Pass@1 和允许重规划后的通过率。
- 不允许行为触发次数。

### 规划指标

- Plan Schema 合法率。
- DAG 合法率。
- 平均步骤数。
- 无效依赖和不必要步骤数。
- 重规划次数。

### 工具指标

- Tool 选择正确率。
- 参数首次合法率。
- 修复后合法率。
- 重复工具调用率。
- Tool Error 恢复率。

### 资源指标

- 首 Token 延迟。
- 总耗时。
- 输入/输出 Token。
- 本地峰值内存/显存。
- API 成本。

### 上下文指标

- Context 使用率。
- 检索命中率。
- 无关上下文比例。
- 压缩次数。
- 关键约束丢失率。

## 13. A/B 对比规则

- 使用同一 Workspace Fixture 和 TaskSpec。
- 固定权限和预算。
- 固定 Agent Core、Prompt 和 Tool 版本。
- 每个 Deployment 多次运行，避免单次随机性。
- 记录是否支持 Seed；不支持时明确标记。
- 结果由确定性断言优先评分，人工或 LLM Judge 作为补充。
- Judge Deployment 与被测 Deployment 分离记录。

## 14. Provider 开发流程

1. 编写协议样本夹具。
2. 实现请求序列化和响应解析。
3. 实现流式聚合。
4. 实现 Tool Call/Result 配对。
5. 实现错误映射和取消。
6. 运行 Provider 契约测试。
7. 运行能力探测。
8. 运行最小 Golden Suite。
9. 更新支持矩阵和文档。

## 15. 验收标准

- 本地和 API Deployment 不修改 Agent Core 即可运行同一任务。
- Provider 原始差异不会泄漏到 Tool Runtime。
- 能力探测失败会关闭对应能力，而不是依赖 Prompt 侥幸使用。
- 评测报告可以复现具体模型、Runtime、量化和参数。
- 本地失败不会在评测中被 API 结果掩盖。
