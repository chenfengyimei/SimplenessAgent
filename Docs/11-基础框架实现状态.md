## 已验证的运行链

`CLI → App Service → SQLite 事务（Task + Event） → Plan DAG → Workspace 边界内只读 Tool → Artifact + Evidence → Step/Task 验证完成 → Checkpoint → 重启读取快照`

这条链路满足“任务、计划、证据和恢复独立于 UI 与聊天记录”的基础决策。当前执行器故意只运行确定性的侦察步骤；模型或副作用尚未接入，因此不会发生未经授权的文件修改。

## 下一阶段开发事项

1. **P0.2 / Provider PoC**：实现 OpenAI-compatible Provider 的文本、流式、Tool Call、取消与能力探测；加入脱敏原始响应夹具。
2. **P1.4 / Agent Worker**：实现固定 System Contract、受控单工具循环、Schema 校验、重复动作与预算停止条件；以 Mock Provider Golden Cases 驱动。
3. **P1.5 / 可写工具**：先完成 Tool Intent、参数哈希、审批票据和幂等恢复测试，再开放 `apply_patch`、受控 `write_file` 与命令工具。
4. **P1.6 / 验证器**：补齐命令、文件和 Diff 断言，生成 FinalReport，禁止无 Evidence 的完成结论。
5. **P2 / 中长任务能力**：Step 边界 Checkpoint、恢复审计、Plan Revision、局部重规划和 Context Budget。
6. **P3-P5**：在核心闭环稳定后实施 FTS5 记忆/项目索引、Skill、单层多 Agent，最后接入 Wails + Vue 任务工作台。

## 明确的范围边界

- 基础框架不把未完成能力标称为“支持”。
- 任何写、危险、网络或外部副作用均保持 fail-closed。
- 前端状态不能成为任务事实来源；后续 UI 仅通过 App Service 的命令/查询与事件流交互。

## 2026-08-11：P0.2 Provider PoC 已完成

- 新增 `internal/provider/openai`：面向 `/v1` OpenAI-compatible 端点的同步 Chat 与 SSE 流式 Chat 适配器。
- Provider 统一归一化文本、结束原因、Token 用量与 Tool Call；Tool 参数以 JSON 原文保留，交由后续 Worker 按工具 Schema 校验后才可执行。
- 扩展 Provider 契约：`ChatStream`、有序 Stream Event、Tool Call/Tool Result 往返消息字段和 Tool 参数 Schema。
- 实现 `/models` 健康检查及受限主动能力探测（文本、流式、工具请求形状）；探测会消耗模型容量，调用方必须传入有超时的 Context。
- 实现认证、限流、超时、取消、上下文溢出、端点不可达和无效响应等规范化错误；Provider 不持久化原始提示或响应，且会从 HTTP 错误消息中移除配置的 API Key。
- 新增本地 `httptest` 覆盖：请求映射、同步 Tool Call 归一化、SSE 文本/Tool Call 聚合、取消分类、能力探测。

仍未接入 CLI、Deployment 持久化或 Agent Worker；基础运行器依旧只执行确定性的只读侦察步骤。下一项为 P1.4 Agent Worker：以本 Provider 和 Mock Provider 驱动受控的只读工具循环、输出 Schema 校验与预算停止条件。

## 2026-08-11：P1.4 Read-only Worker 已完成首个增量

- 新增 `internal/worker`：固定 Executor System Contract 下的模型驱动、单工具顺序循环。
- Worker 只暴露 Step allowlist 中已注册、带参数 Schema 的 `READ` 工具；未授权工具、写工具、无效 Tool Call/参数和重复动作均在执行前 fail-closed。
- 支持受限 JSON Schema 子集（对象、必填字段、额外字段、数组、基本类型和枚举）；未知 Schema 关键字也会拒绝，避免“声明比实际校验更严格”的假象。
- 强制 Step 迭代、输入/输出 Token 与最大时长预算；返回模型文本、工具结果与用量，但不推进 Task/Step 状态或采纳模型的完成声明。
- Golden Cases 覆盖正常只读闭环、越权工具、Schema 失败、重复调用、写工具拒绝及 Token/时长预算停止。

当前 CLI 仍维持确定性侦察路径，尚未调用 Worker。下一增量需要将 Worker 接入受版本控制的 Plan/Step 调度，并实现 Verifier 与 FinalReport，使状态完成只能来自可验证 Evidence。

## 2026-08-11：P1.4 模型驱动规划已完成首个增量

- 新增 `internal/planner`：Planner 仅提交 `PlanVersion` JSON 候选；不执行工具、不写状态、不持久化计划。
- 本地层重新生成 Plan ID、绑定 Task/Revision/Parent Plan/时间与 Agent 身份，拒绝多余 JSON、无效 DAG、超出步骤数、非只读工具、未授权工具和未界定的 Step 预算。
- Planner 只能看到已提供的 schema-bound `READ` 工具，且不向模型提供任何可执行 Tool Call；模型请求与计划 Token 用量均受 Task 预算限制。
- Golden Cases 覆盖正常候选接纳、模型伪造元数据隔离、非 JSON 输出及越权写工具计划拒绝。

仍未将 Planner 接入 App Service 的 `CreateTask` 事务路径；当前 CLI 继续生成确定性的初始 Plan。下一步是在保留该安全回退的前提下，增加可配置的 Deployment/Planner 入口和 Plan 版本持久化审计。

## 2026-08-11：Deployment 与能力快照持久化

- 新增版本化 Deployment 与 CapabilitySnapshot 持久化、前向 SQLite 迁移和 App Service 探测入口。
- Deployment 仅保存 CredentialRef，不保存密钥明文；Provider 由运行时解析器注入。
- Probe 会持久化能力快照并回链 Deployment，已用 Mock Provider 验证重启前读取链路。

## 2026-08-11：Planner 已接入受审计计划版本

- App Service 可通过已启用 Deployment 解析 Provider、注册工作区只读工具、生成本地校验的下一 Plan Revision，并与 `PLAN_CREATED` 事件原子保存。
- 未配置 Provider、禁用 Deployment 或校验失败均 fail-closed；现有 CLI 创建任务仍使用确定性初始 Plan。

## 2026-08-11：P1.6 Evidence 验证与 FinalReport

- 新增确定性 Verifier 与 FinalReport：仅接受持久化且已验证、类型匹配的 Evidence。
- `RunTask` 在进入 `COMPLETED` 前强制验证 Task 接收条件；失败则转为 `FAILED`，禁止无 Evidence 的完成结论。
- 当前支持 `EVIDENCE_EXISTS`；其他接收类型以 fail-closed 方式报告未实现，待命令/文件/Diff 验证器增量补齐。
- 每次任务验证都会将 FinalReport 以 `FINAL_REPORT` 内容寻址 Artifact 落库；报告写入失败同样会阻止完成状态。
- `FILE_EXISTS` 已接入：仅在 Task 的授权 Workspace 内验证常规文件，目录、缺失文件与路径逃逸均失败。
## 2026-08-11：P1.5 Tool Intent 与审批票据

- 新增规范化参数哈希、作用域绑定的幂等键、持久化 `INTENT_RECORDED` 工具调用记录及参数绑定审批票据。
- 相同幂等键恢复时复用原 Intent；审批消费在 SQLite 单事务中精确匹配 Task、Step、工具、参数哈希、有效期和剩余次数。
- 写工具仍未开放；本增量只提供其必须先满足的 write-ahead 与 approval 基础。

## 2026-08-11：P1.5 受审批 `write_file` 执行器

- 新增显式注册的 `write_file`：仅接受路径、UTF-8 内容和当前内容哈希；先校验参数、授权工作区边界与目标版本，再进入审批边界。
- 审批回调必须在原子写入之前成功；写入使用同目录临时文件、`Sync` 和重命名替换，哈希冲突或审批拒绝均不修改目标文件。
- 该执行器未默认注册到 Worker，也尚未由 CLI 暴露；持久化 Intent 与一次性 ApprovalTicket 的接线见后续本版本记录。

## 2026-08-11：P1.5 持久化审批与幂等恢复已接线

- App Service 新增 `ApproveWriteFile` 与 `WriteFile`：审批只绑定当前 Plan 中声明 `write_file` 的 `WRITE` Step；执行还要求 Task/Step 正处于 `RUNNING`，并再次检查路径在 Step 工作区范围内。
- 首次 Tool Intent 与 `TOOL_INTENT_RECORDED`、审批票据与 `TOOL_APPROVED` 分别在 SQLite 单事务内持久化；票据精确匹配 Task、Step、工具、参数哈希、到期时间和剩余次数。
- 工具结果回写相同 Intent。若写后重启或重复调用，文件已达到目标内容时返回恢复成功，不再消耗审批或重复写入审计事件。
- `write_file` 仍未注册到 Worker 或 CLI；下一步将把受控写工具引入执行调度，并为模型产生的非只读 Plan 补充能力与审批边界。
