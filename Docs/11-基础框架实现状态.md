## 已验证的运行链

`CLI → App Service → SQLite 事务（Task + Event） → Plan DAG → Workspace 边界内只读 Tool → Artifact + Evidence → Step/Task 验证完成 → Checkpoint → 重启读取快照`

这条链路满足“任务、计划、证据和恢复独立于 UI 与聊天记录”的基础决策。确定性侦察、模型驱动的受预算只读步骤、受审批 `write_file`、结构化 Handoff 和桌面查询/创建命令均已接入；写工具仍不注册给模型，因而不会发生未经审批的文件修改。

4. **P1.6 / 验证器**：补齐命令、文件和 Diff 断言，生成 FinalReport，禁止无 Evidence 的完成结论。
5. **P2 / 中长任务能力**：Step 边界 Checkpoint、恢复审计、Plan Revision、局部重规划和 Context Budget。

## 明确的范围边界

- 基础框架不把未完成能力标称为“支持”。
- 任何写、危险、网络或外部副作用均保持 fail-closed。
- 前端状态不能成为任务事实来源；后续 UI 仅通过 App Service 的命令/查询与事件流交互。

## 2026-08-11：P0.2 Provider PoC 已完成

- 新增 `internal/provider/openai`：面向 `/v1` OpenAI-compatible 端点的同步 Chat 与 SSE 流式 Chat 适配器。
- Provider 统一归一化文本、结束原因、Token 用量与 Tool Call；Tool 参数以 JSON 原文保留，交由后续 Worker 按工具 Schema 校验后才可执行。
- 扩展 Provider 契约：`ChatStream`、有序 Stream Event、Tool Call/Tool Result 往返消息字段和 Tool 参数 Schema。
- 实现 `/models` 健康检查及受限主动能力探测（文本、流式、工具请求形状）；探测会消耗模型容量，调用方必须传入有超时的 Context。
- 实现认证、限流、超时、取消、上下文溢出、端点不可达和无效响应等规范化错误；Provider 不持久化原始提示或响应，且会从 HTTP 错误消息中移除配置的 API Key。
- 新增本地 `httptest` 覆盖：请求映射、同步 Tool Call 归一化、SSE 文本/Tool Call 聚合、取消分类、能力探测。

仍未接入 CLI、Deployment 持久化或 Agent Worker；基础运行器依旧只执行确定性的只读侦察步骤。下一项为 P1.4 Agent Worker：以本 Provider 和 Mock Provider 驱动受控的只读工具循环、输出 Schema 校验与预算停止条件。

## 2026-08-11：P1.4 Read-only Worker 已完成首个增量

- 新增 `internal/worker`：固定 Executor System Contract 下的模型驱动、单工具顺序循环。
- Worker 只暴露 Step allowlist 中已注册、带参数 Schema 的 `READ` 工具；未授权工具、写工具、无效 Tool Call/参数和重复动作均在执行前 fail-closed。
- 支持受限 JSON Schema 子集（对象、必填字段、额外字段、数组、基本类型和枚举）；未知 Schema 关键字也会拒绝，避免“声明比实际校验更严格”的假象。
- 强制 Step 迭代、输入/输出 Token 与最大时长预算；返回模型文本、工具结果与用量，但不推进 Task/Step 状态或采纳模型的完成声明。
- Golden Cases 覆盖正常只读闭环、越权工具、Schema 失败、重复调用、写工具拒绝及 Token/时长预算停止。

当前 CLI 仍维持确定性侦察路径，尚未调用 Worker。下一增量需要将 Worker 接入受版本控制的 Plan/Step 调度，并实现 Verifier 与 FinalReport，使状态完成只能来自可验证 Evidence。

## 2026-08-11：P1.4 模型驱动规划已完成首个增量

- 新增 `internal/planner`：Planner 仅提交 `PlanVersion` JSON 候选；不执行工具、不写状态、不持久化计划。
- 本地层重新生成 Plan ID、绑定 Task/Revision/Parent Plan/时间与 Agent 身份，拒绝多余 JSON、无效 DAG、超出步骤数、非只读工具、未授权工具和未界定的 Step 预算。
- Planner 只能看到已提供的 schema-bound `READ` 工具，且不向模型提供任何可执行 Tool Call；模型请求与计划 Token 用量均受 Task 预算限制。
- Golden Cases 覆盖正常候选接纳、模型伪造元数据隔离、非 JSON 输出及越权写工具计划拒绝。

仍未将 Planner 接入 App Service 的 `CreateTask` 事务路径；当前 CLI 继续生成确定性的初始 Plan。下一步是在保留该安全回退的前提下，增加可配置的 Deployment/Planner 入口和 Plan 版本持久化审计。

- App Service 可通过已启用 Deployment 解析 Provider、注册工作区只读工具、生成本地校验的下一 Plan Revision，并与 `PLAN_CREATED` 事件原子保存。
- 未配置 Provider、禁用 Deployment 或校验失败均 fail-closed；现有 CLI 创建任务仍使用确定性初始 Plan。

## 2026-08-11：P1.6 Evidence 验证与 FinalReport

- 新增确定性 Verifier 与 FinalReport：仅接受持久化且已验证、类型匹配的 Evidence。
- `RunTask` 在进入 `COMPLETED` 前强制验证 Task 接收条件；失败则转为 `FAILED`，禁止无 Evidence 的完成结论。
- 当前支持 `EVIDENCE_EXISTS`；其他接收类型以 fail-closed 方式报告未实现，待命令/文件/Diff 验证器增量补齐。
- 每次任务验证都会将 FinalReport 以 `FINAL_REPORT` 内容寻址 Artifact 落库；报告写入失败同样会阻止完成状态。
- `FILE_EXISTS` 已接入：仅在 Task 的授权 Workspace 内验证常规文件，目录、缺失文件与路径逃逸均失败。
## 2026-08-11：P1.5 Tool Intent 与审批票据

- 新增规范化参数哈希、作用域绑定的幂等键、持久化 `INTENT_RECORDED` 工具调用记录及参数绑定审批票据。
- 相同幂等键恢复时复用原 Intent；审批消费在 SQLite 单事务中精确匹配 Task、Step、工具、参数哈希、有效期和剩余次数。
- 写工具仍未开放；本增量只提供其必须先满足的 write-ahead 与 approval 基础。

## 2026-08-11：P1.5 受审批 `write_file` 执行器

- 新增显式注册的 `write_file`：仅接受路径、UTF-8 内容和当前内容哈希；先校验参数、授权工作区边界与目标版本，再进入审批边界。
- 审批回调必须在原子写入之前成功；写入使用同目录临时文件、`Sync` 和重命名替换，哈希冲突或审批拒绝均不修改目标文件。
- 该执行器未默认注册到 Worker，也尚未由 CLI 暴露；持久化 Intent 与一次性 ApprovalTicket 的接线见后续本版本记录。

## 2026-08-11：P1.5 持久化审批与幂等恢复已接线

- App Service 新增 `ApproveWriteFile` 与 `WriteFile`：审批只绑定当前 Plan 中声明 `write_file` 的 `WRITE` Step；执行还要求 Task/Step 正处于 `RUNNING`，并再次检查路径在 Step 工作区范围内。
- 首次 Tool Intent 与 `TOOL_INTENT_RECORDED`、审批票据与 `TOOL_APPROVED` 分别在 SQLite 单事务内持久化；票据精确匹配 Task、Step、工具、参数哈希、到期时间和剩余次数。
- 工具结果回写相同 Intent。若写后重启或重复调用，文件已达到目标内容时返回恢复成功，不再消耗审批或重复写入审计事件。
- `write_file` 仍未注册到 Worker 或 CLI；下一步将把受控写工具引入执行调度，并为模型产生的非只读 Plan 补充能力与审批边界。

## 2026-08-11：P2 运行边界 Checkpoint 与安全恢复

- Checkpoint 现在是版本化的可读取契约；任务进入实际执行边界后立即保存快照，终态也会保存最新快照，同一事件序列不会重复写入。
- 新增 `RecoverRunningTask`：对进程中断遗留的 `RUNNING` Task，先保存观察快照，再以事件 `TASK_RECOVERY_PAUSED` 原子转为 `PAUSED`，并保存恢复后的快照。
- 恢复路径坚持 fail-closed：不自动重放 Step、Tool 或任何副作用；后续由局部重规划/显式调度决定继续方式，已持久化的 Tool Intent 可用于安全判断。

## 2026-08-11：P2 局部重规划

- 新增 `ReplanTask`：仅 `PAUSED` Task 可以重规划；前一版 Plan Revision 与 `MaxReplans` 预算会在模型调用前校验，耗尽预算时 fail-closed。
- 模型仅接收 Task、授权的只读工具、前一版 Plan、持久化 Step 状态和操作原因；新 Revision 必须使用全新的 Step ID，禁止把旧 Step 当作可重放命令。
- 通过本地 DAG/工具/预算校验的新 Plan 以 `PLAN_REPLANNED` 事件落库，再将 Task 从 `PAUSED` 切回 `READY`。这不会自动执行或重放工具，仍由后续调度器控制。

## 2026-08-11：P2 Context Package 编译器

- 新增版本化 `ContextPackage`、带来源的 `ContextSection` 与输入/预留/已用 Token 预算契约；上下文不再只能以未受控字符串传递。
- 编译器在预留输出 Token 后按优先级选取段落，同一来源默认只允许一个段落，来源会排序去重，未选段落作为可审计的省略结果返回。
- 无任何有效段落可放入预算时返回 `CONTEXT_OVERFLOW`，避免把空或超限上下文提交给模型。

## 2026-08-11：P2 Worker Context Package 接线

- Worker 输入支持 `ContextPackage`：存在 Package 时只渲染其编译后段落和来源引用，自由字符串字段仅作为旧调用者的兼容后备，避免绕过编译器的调用路径继续扩张。
- Worker 在 Provider 调用前校验 Context Package 版本、必需标识、Step 绑定、段落 Token 之和与预算；无效或超限上下文直接拒绝，不会发起模型请求。
- Planner 的系统上下文编译与持久化预览尚待后续增量；当前已完成执行器侧的受预算模型输入边界。

## 2026-08-11：P1.6 Diff 接受条件验证

- 新增 `DIFF_CONTAINS`：Task 可声明授权工作区内某文件的 `git diff HEAD` 必须包含的文本；验证结果由 FinalReport 持久化，不依赖模型完成声明。
- Git 调用使用固定参数、无 shell、禁用外部 diff/颜色输出并设置五秒超时；非 Git 工作区、缺少提交基线、路径逃逸、超时和内容不匹配均 fail-closed。
- 任意命令断言仍未开放，后续会以独立的受控命令 Tool、审批和 Evidence 机制实现；当前 diff 验证仅执行只读 Git 查询。

## 2026-08-11：P3 结构化记忆与 FTS5

- 新增版本化 `MemoryRecord`、`memory_records` 及可重建的 SQLite FTS5 索引。写入必须具有 Workspace 作用域、Event/Artifact 来源、置信度、重要性、状态和创建来源；正文哈希由本地确定性计算。
- 新增 `CreateMemory`/`SearchMemory` App Service 入口。检索严格限定 Workspace，仅返回 `ACTIVE`/`PINNED` 且未过期记录，按 FTS BM25 和重要性排序。
- 自动候选提炼、记忆冲突/替代关系、向量混合检索与自动注入模型调用仍待后续增量；当前阶段不把模型输出自动写为长期记忆。

## 2026-08-11：P3 记忆检索到 Context Package

- 新增显式 `CompileMemoryContext`：从当前 Task 的 Workspace 检索可用记忆，转为 `MEMORY_*` ContextSection 后再进入统一 Token 预算与来源多样性编译器。
- 每段记忆保留 `memory:<id>` 及其源 Event/Artifact 引用；优先级由置信度与重要性乘积决定。归档、过期、其他 Workspace 的记录不会参与当前上下文。
- 该能力尚不自动接入所有 Planner/Worker 请求，调用方必须明确选择检索查询；这避免当前阶段的宽泛召回造成提示污染。

## 2026-08-11：P3 本地 Skill 运行时基座

- 新增工作区 `.simpleness/skills/<name>/skill.json` 与按需 `SKILL.md` 加载。`ListSkills` 只读取经校验的 manifest，`LoadSkill` 才读取正文，支持渐进式提示注入。
- Manifest 绑定版本、名称、说明、工具白名单和工作区 Scope；加载器拒绝未知工具、越界 Scope、符号链接、超大文件和多 JSON 值。Skill 不执行脚本，也不能提升权限。
- 当前 App 仅向 Skill 加载器提供已注册的只读工具，因此声明写工具会被拒绝。Skill 安装、持久化版本管理和选择策略将作为后续增量实现。

## 2026-08-11：P3 Worker Skill 边界

- Worker 支持显式传入已加载 Skill，并在模型请求中渲染其指令；Skill 必须有已验证的 Context Package，正文 Token 会与该 Package 已用 Token 一并受到剩余预算限制。
- Worker 在调用 Provider 前强制检查 Skill 版本/完整性、名称去重、工具白名单是 Step 白名单子集，以及 Skill Scope 不宽于 Step Scope。越界或超预算的 Skill 不会到达模型。
- Skill 仅提供附加指令，不能扩大实际 Tool Registry、修改审批票据或绕过 READ 风险限制。

## 2026-08-11：模型驱动单步骤执行闭环

- 新增 `RunModelStep` App Service：仅允许 `READY` Task 的唯一 Ready `READ` Step 使用已启用 Deployment；运行时只注册只读工具并构造受预算的 Task/Plan/Step Context Package。
- Worker 的文本、工具结果、Token 用量与迭代次数被保存为内容寻址 `AGENT_REPORT` Artifact，并产生已验证 Evidence；随后才执行 Step/Task 状态转换与 FinalReport 接收条件验证。
- Worker 错误会使运行中的 Step/Task 失败；此入口不注册写工具、不消费审批票据，也不将模型的完成声明直接当作任务完成事实。

## 2026-08-11：模型工作流 CLI

- CLI 新增 `deployment add|list|probe`、`task plan --deployment` 与 `task run-model`；已持久化的 OpenAI-compatible Deployment 可通过同一 JSON CLI 驱动模型规划和单个受控只读步骤。
- API Key 只在调用进程通过 `SIMPLENESS_API_KEY` 提供，数据库仅保存可选的不透明凭据引用；本地无认证 Runtime 不需设置该变量。
- `run-model` 仍只执行唯一就绪的 `READ` Step，持久化 `AGENT_REPORT`/Evidence，再由确定性验证器决定完成，写工具和审批边界不会因 CLI 接线而放宽。

## 2026-08-11：受控命令接受条件

- `COMMAND` 已接入确定性验证器，但不是通用 shell：当前仅支持 `go_test` 与 `go_vet` 两个声明式 runner，`packages` 必须为显式工作区相对 Go 包路径。
- 验证固定在授权工作区运行，使用当前 Go runtime，默认 30 秒、最长 60 秒，输出最多 1 MiB；未知 runner、包路径逃逸、超时、输出超限或非零退出全部 fail-closed。
- 此能力只用于最终接受条件，仍不会把任意命令工具注册给模型，也不改变写入审批边界。

## 2026-08-11：单层 Agent Assignment

- 新增版本化、SQLite 持久化的 `AgentAssignment` 与 `AGENT_ASSIGNED` 事件。Coordinator 只能为显式允许子 Agent 的 `READY` Task 分配依赖已满足的只读 Step。
- Assignment 固定深度为 1，并在创建时快照 Step 的工具白名单和工作区 Scope；同一 Step 同时只允许一个 `PENDING` 或 `RUNNING` Assignment。
- 当前只交付可恢复、可审计的分配边界，尚未启动子 Agent Worker、递归创建、自由 Agent Chat 或并行写入。

## 2026-08-11：同步单子 Agent 与 Handoff

- 新增 `RunAssignedAgent`：只接受深度 1、`PENDING` 的 Assignment，复用受控只读模型执行，并以独立 `AGENT_STATUS_CHANGED` 事件记录运行、成功或失败。
- 成功后生成 `AGENT_HANDOFF` Artifact，仅包含已持久化 Agent Report 的 Artifact/Evidence 引用；任务 Artifact 查询可供 Coordinator 和未来 UI 重读这份交接事实。
- 没有递归 Assignment、自由 Agent Chat、未受控上下文继承或写权限扩张；下一步才会在此基础上考虑有界的 Coordinator 调度。

## 2026-08-11：有界 Coordinator Cycle

- 新增 `RunCoordinatorCycle`：仅对显式启用子 Agent 的 `READY` Task，调度唯一依赖就绪的只读 Step；若已有 `PENDING` Assignment 则复用，否则以 Step 的 `PreferredRole` 创建后同步执行。
- 当前 Plan 与 Assignment 的工具/Scope 快照不再一致、存在多个 Ready Step 或运行中的 Assignment 时都会拒绝调度，避免在尚未完成冲突分析前隐式并行或重放。

## 2026-08-11：Agent Assignment 安全恢复

- 新增 `RecoverRunningAgentAssignments`：中断遗留的 `RUNNING` Assignment 先记录 `AGENT_RECOVERY_FAILED`，再将父 Task 经 Checkpoint 转为 `PAUSED`。
- 恢复不自动重放模型请求、工具调用、Handoff 或 Assignment；后续必须显式重规划或调度，保持副作用恢复的 fail-closed 原则。

## 2026-08-11：Wails + Vue 桌面工作台基座

- 新增 `desktop/` Wails v2 + Vue TypeScript 子项目；它通过 App Service 打开同一用户配置数据目录，只读取 Task Snapshot，前端不拥有业务事实。
- 首屏工作台显示任务状态、Step 数和 Event 数并可刷新。Binding 不提供模型调用、凭据、写工具、审批或递归 Agent 控制。
- 已验证前端生产构建、桌面 Go 子模块 `go test`/`go vet`，以及 Windows Wails 生产构建产生 `desktop/build/bin/desktop.exe`。

## 2026-08-11：桌面受控 Core 命令

- 桌面 Binding 新增 `ListWorkspaces`、`CreateWorkspace` 与 `CreateTask`，直接调用既有 App Service，所有路径校验、状态转换与事件审计仍由 Core 执行。
- Vue 工作台加入工作区和任务创建表单。前端不会拼接 SQL、直接写 Artifact 或维护第二份任务状态，而是在命令成功后刷新 Task Snapshot。

## 2026-08-11：P0-P5 路线完成审计

- Provider 的同步/流式 Tool Call、能力探测与 CLI Deployment；模型规划、受预算只读 Worker、`AGENT_REPORT`/Evidence/FinalReport；审批写入、幂等 Intent 与恢复；P2 Context/Memory/Skill；单层 Assignment/Handoff/Coordinator，以及 Wails + Vue 工作台均已有实现和对应测试或生产构建验证。
