# SimplenessAgent 记忆与上下文系统

## 1. 设计目标

记忆系统解决的不是“让 AI 永远记得聊天”，而是：

- 在当前步骤需要时快速找到正确事实。
- 在长任务压缩或接力后保留目标、约束和进度。
- 保存用户确认的偏好和项目决策。
- 从成功和失败任务中复用经验。
- 避免错误、过时或无来源的记忆污染后续任务。

## 2. 核心原则

- 原始 Event 和 Artifact 是事实，Memory 是可重建派生数据。
- 记忆必须有作用域和来源。
- 记忆写入比检索更严格。
- 冲突信息建立关系，不静默覆盖。
- Context Compiler 按当前 Step 检索，不按整段会话无差别召回。
- 不以一段不断改写的“总摘要”作为唯一长期状态。

## 3. 记忆分层

### 3.1 Working Memory

当前 Run 的操作状态：

- TaskSpec。
- 当前 PlanVersion。
- Step 状态。
- 未决问题和审批。
- 当前预算。
- 最近原子消息。

Working Memory 主要来自结构化表和 Checkpoint，不依赖向量检索。

### 3.2 Episodic Memory

过去任务经历：

- 任务结果。
- 使用过的方法。
- 失败原因和恢复方法。
- 验证结果。
- 关键 Artifact。

### 3.3 Semantic Memory

项目和领域知识：

- 架构说明。
- 代码符号和路径。
- 配置含义。
- 业务术语。
- 参考文档。

### 3.4 User Memory

- 用户明确偏好。
- 长期约束。
- 常用环境。
- 用户确认的事实和决策。

敏感信息默认不自动进入 User Memory。

### 3.5 Procedural Memory

- Skills。
- SOP。
- 模板。
- 工具使用规范。
- 已验证的任务模式。

## 4. 记忆对象

```json
{
  "id": "mem_xxx",
  "version": 1,
  "type": "DECISION",
  "scope": {
    "workspace_id": "ws_xxx",
    "user_id": "local-user",
    "task_id": null
  },
  "title": "默认数据库选择",
  "content": "项目默认使用 SQLite WAL，不依赖外部数据库。",
  "tags": ["architecture", "database"],
  "entities": ["SQLite", "WAL"],
  "source_event_ids": ["evt_xxx"],
  "source_artifact_ids": ["art_xxx"],
  "confidence": 1.0,
  "importance": 0.9,
  "status": "ACTIVE",
  "valid_from": "2026-08-11T00:00:00Z",
  "valid_until": null,
  "supersedes": null,
  "created_by": "USER_CONFIRMED",
  "content_hash": "sha256:..."
}
```

## 5. 记忆类型

- `FACT`：可验证事实。
- `DECISION`：已做出的决定及理由。
- `CONSTRAINT`：不得违反的长期或项目限制。
- `PREFERENCE`：用户偏好。
- `TASK_PROGRESS`：跨会话仍有用的任务进度。
- `REFERENCE`：重要资料和引用。
- `LESSON`：从失败或成功中得到的经验。
- `RELATION`：实体间关系。

## 6. 记忆写入流程

```mermaid
flowchart LR
    EVENT["Event/Artifact"] --> CAND["候选提取"]
    CAND --> SCHEMA["Schema 校验"]
    SCHEMA --> SOURCE["来源与作用域校验"]
    SOURCE --> SENSITIVE["敏感信息策略"]
    SENSITIVE --> DEDUP["去重与相似检测"]
    DEDUP --> CONFLICT["冲突/替代分析"]
    CONFLICT --> SCORE["置信度与重要性"]
    SCORE --> COMMIT["提交 Memory"]
    COMMIT --> INDEX["FTS/Vector 索引"]
```

### 6.1 候选提取

触发条件：

- 用户明确说“记住”。
- 用户确认项目决策。
- Task 完成或失败。
- 生成重要 Artifact。
- 达到事件数量或 Token 阈值。

不对每条消息都进行模型抽取。

### 6.2 确定性预处理

先用程序提取：

- Task、Step、路径、命令和 Artifact ID。
- 用户显式确认标志。
- 时间、Workspace 和来源。
- 已存在相同哈希。

只有语义提炼才交给模型。

### 6.3 冲突处理

新记忆与旧记忆冲突时：

- 新内容有明确用户确认：旧记忆标记 `SUPERSEDED`。
- 新内容来自自动推断：保存为候选，等待确认或更多证据。
- 两者适用范围不同：保留并细化 Scope。

## 7. 记忆生命周期

状态：

- `CANDIDATE`
- `ACTIVE`
- `PINNED`
- `ARCHIVED`
- `SUPPRESSED`
- `SUPERSEDED`
- `DELETED/TOMBSTONED`

系统自动检索只返回 ACTIVE/PINNED 且在有效期内的内容。

删除策略：

- 派生索引可以物理删除。
- 记忆正文按用户隐私请求删除。
- 关联事件若属于任务审计事实，使用 Tombstone 和内容脱敏；具体策略在隐私 ADR 中确定。

## 8. 项目知识摄取

### 8.1 原始层

代码和文档保持原样，只读索引，不由 AI 自动改写源文件。

### 8.2 结构化索引层

保存：

- 文件路径。
- Git Revision 或文件哈希。
- 语言/MIME。
- 标题、符号、段落和行范围。
- 父子分块关系。
- Workspace 和权限 Scope。

### 8.3 AI 整理层

可生成架构页、模块摘要和术语页，但必须引用原始文件及版本。整理层可重建，不作为源代码事实替代品。

## 9. 分块策略

按内容类型选择：

- Markdown：标题层级和段落。
- 代码：符号、函数、类型和相邻注释。
- 配置：顶级键或逻辑块。
- 日志：时间窗口和错误边界。
- 对话：完整用户—助手—工具原子轮次。

分块保留父级摘要和相邻关系。禁止仅按固定字符数无脑切分所有内容。

## 10. 检索流程

### 10.1 查询生成

根据当前 Role 和 Step 生成多个查询：

- 目标关键词。
- 文件/模块实体。
- 失败错误。
- 所需决策或历史经验。

查询生成失败时使用 Step 标题、输入和错误码构造确定性查询。

### 10.2 硬过滤

优先过滤：

- Workspace。
- 用户。
- Task/Run。
- Memory Type。
- 状态和有效期。
- 路径或语言。
- 权限 Scope。

### 10.3 混合召回

- FTS5/BM25 或 n-gram。
- 向量相似度。
- 最近和高重要性记忆。
- 计划、Artifact 和实体关系。

使用 RRF 等排名融合，避免直接加总不同量纲的分数。

### 10.4 Rerank 与裁剪

Rerank 为可选能力。本地资源不足时使用规则和融合排序。最终按 Context Budget 和来源多样性裁剪。

## 11. Context Package

每次模型调用的上下文分区：

1. 固定 System Contract。
2. 当前 Role。
3. Task 目标、约束和验收标准。
4. 当前 Plan 与 Step。
5. 最近相关消息。
6. 检索记忆和项目知识。
7. 选中的 Skill。
8. Tool Schema。
9. Artifact 摘要或片段。
10. 输出和推理预留。

建议默认不超过 Deployment 可靠上下文的 60%—70%，为 Tool Result、Thinking 和最终输出保留空间。

示例预算仅作为初值：

| 分区 | 建议范围 |
|---|---:|
| System/Role Contract | 8%—12% |
| Task/Plan/Step | 10%—15% |
| 最近消息 | 10%—20% |
| 检索知识与记忆 | 20%—25% |
| Skill/Tool Schema | 5%—10% |
| 推理、工具结果和输出预留 | 至少 25% |

预算由 Model Profile 和实际探测调整。

## 12. 上下文压缩

压缩优先级：

1. 将完整 Tool Result 外置为 Artifact。
2. 去除重复或低分检索内容。
3. 用结构化摘要替换已完成步骤细节。
4. 压缩较旧消息，但保持 Tool Call/Result 原子性。
5. 生成新的 Checkpoint/Handoff。

结构化压缩结果至少包括：

- Goal。
- Non-goals。
- Constraints。
- Decisions。
- Plan Version。
- Completed/Failed/Blocked Steps。
- Artifacts/Evidence。
- Open Questions。
- Next Ready Steps。

压缩不能覆盖原始事件。

## 13. Token 计数

优先级：

1. Deployment 提供准确 Tokenize 接口。
2. 本地加载对应 Tokenizer。
3. 语言感知的保守估算并加安全余量。

不能为所有模型硬编码同一个字符/Token 比例。

## 14. 记忆健康审计

定期检查：

- 无来源记忆。
- 失效 Artifact 引用。
- 过期记忆。
- 高相似重复。
- 相互冲突且未建立关系。
- 长期从未命中。
- 过长、模糊、含多个事实的记忆。
- 索引版本与 Embedding 版本不一致。

修复操作默认 Dry Run，涉及删除和合并时可回滚。

## 15. 用户可控性

用户能够：

- 预览某次模型调用的完整 Context Package。
- 查看每条记忆的来源和命中原因。
- 固定、修改、压制、归档和删除记忆。
- 关闭某类自动提取。
- 限制某个 Workspace 的长期记忆。
- 导出和重建记忆索引。

## 16. 开发顺序

1. Working Memory 和 Checkpoint。
2. Artifact 外置和 Context Budget。
3. FTS5 项目索引。
4. 结构化 Memory CRUD 与来源。
5. 自动候选提取。
6. 混合检索和向量接口。
7. 冲突、审计和调试界面。

优先保证结构正确，再增加向量和模型提炼能力。

## 17. 验收场景

- 经过多次压缩后，硬约束仍能被检索和注入。
- 用户修改架构决策后，旧决策不再自动生效但仍可追溯。
- 删除向量索引后可从 SQLite/Artifact 重建。
- 任务接力时不读取全部原始会话也能继续。
- 恶意 Tool Result 内容不会被当作系统指令注入。
- 无关记忆数量增加后，关键记忆召回质量仍在基线范围内。
