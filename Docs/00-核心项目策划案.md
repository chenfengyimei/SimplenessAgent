# SimplenessAgent 核心项目策划案

> 文档性质：项目立项与产品方向基线  
> 目标读者：项目负责人、架构师、开发者、测试人员、未来贡献者

## 1. 项目背景

现有 Agent 产品普遍存在以下问题：

1. 把模型能力当作系统能力，模型一旦变弱，整个任务链路立即失效。
2. 把完整聊天历史当作记忆，导致 Token 不断增长、关键信息逐步丢失。
3. 计划停留在自然语言层面，无法持久化、校验、恢复或精确重试。
4. 工具调用缺少统一协议、权限、幂等和验证，长任务容易产生重复副作用。
5. 多 Agent 追求数量和讨论形式，却没有解决上下文隔离、结果交接和任务恢复。
6. 本地模型、量化模型和 API 模型走不同执行路径，导致测试结果不可比较。
7. 产品界面只展示聊天消息，用户看不到任务为何卡住、做过什么、还差什么。

SimplenessAgent 希望从这些工程问题出发，构建一套真正可以长期开发和实际使用的本地 Agent 框架。

## 2. 项目最初目的

本项目的最初目的不是追求宏大叙事，也不是用更多 Agent 和更多工具堆砌功能，而是建立一个可靠基础：

> 让 `Qwen3.6-35B-A3B` 这一类可本地运行、总体能力较强但仍需要明确约束和上下文管理的模型，能够稳定、顺畅地完成多步骤真实任务。

如果这样的模型可以在框架内稳定工作，更强模型可以获得更高上限，更小模型也可以通过更窄的任务、更多确定性约束和更好的上下文获得实用能力。

## 3. 项目愿景

SimplenessAgent 最终应成为一款安装后即可打开使用的本地桌面软件，同时具备可独立复用的 Agent Core。

用户能够：

- 连接本地 Qwen 模型或远程 API。
- 选择工作目录并提出真实任务。
- 在执行前看到目标、约束、计划和风险。
- 在执行中看到步骤、工具、证据、成本和上下文状态。
- 在程序退出或崩溃后恢复任务。
- 让子 Agent 分担独立步骤，并通过结构化结果接力。
- 查看、修正、固定或删除系统记忆。
- 将成功流程沉淀为可复用 Skill。

## 4. 产品定位

### 4.1 一句话定位

面向本地与 API 模型的可靠任务执行型 Agent 桌面框架。

### 4.2 不是以下产品

- 不是单纯聊天机器人。
- 不是依赖云端服务才能启动的 SaaS。
- 不是第一阶段就覆盖所有办公和浏览器场景的超级应用。
- 不是让多个 Agent 无限讨论的“群聊系统”。
- 不是把 LangChain、LangGraph 或某个模型 SDK 再包装一层。
- 不是以未经验证的模型思考内容作为任务状态的系统。

### 4.3 核心差异

| 常见 Agent | SimplenessAgent |
|---|---|
| 以聊天消息为中心 | 以 Task、Plan、Step 和 Evidence 为中心 |
| 模型自由推进 | 确定性状态机推进 |
| 依赖长上下文 | 使用上下文编译、检索和结构化 Checkpoint |
| 计划是一段文字 | 计划是版本化 DAG 数据 |
| 工具执行后只返回文本 | 工具产生标准结果、证据和 Artifact |
| 子 Agent 返回一段总结 | 子 Agent 返回结构化 AgentReport/Handoff |
| 本地模型与 API 两套逻辑 | 同一 Agent Core、不同 Deployment |
| 失败后重新开始 | 按步骤恢复、重试或有界重规划 |

## 5. 目标用户

### 5.1 首要用户

- 希望在个人电脑运行本地模型的开发者。
- 对数据隐私、本地文件和代码安全有要求的用户。
- 希望比较本地模型与 API 模型实际 Agent 效果的研究者或开发者。
- 希望二次开发 Agent 工具、Skill 和模型适配器的贡献者。

### 5.2 后续用户

- 小团队内部开发助手。
- 企业内网的本地知识与任务执行助手。
- 需要可审计自动化流程的运维和数据人员。

## 6. 首期核心场景

### 6.1 本地代码任务

- 阅读项目结构。
- 定位 Bug。
- 形成修改计划。
- 修改有限文件。
- 运行测试。
- 根据失败结果修正。
- 输出变更说明和证据。

### 6.2 本地终端任务

- 检查环境和服务状态。
- 执行有超时控制的命令。
- 识别长运行任务和交互式提示。
- 等待、收集输出、终止或恢复。

### 6.3 项目知识任务

- 索引本地代码和文档。
- 从历史任务中检索决策、失败经验和用户偏好。
- 在有限上下文中快速获得当前步骤所需知识。

### 6.4 模型对比评测

- 同一任务分别运行本地 Qwen 和 API 模型。
- 比较任务成功率、工具调用、耗时、Token、成本和恢复能力。
- 保存可复现的 Deployment Fingerprint。

## 7. 项目目标

### 7.1 产品目标

- 最终能够打包成 Windows 桌面软件，用户安装后即可打开。
- 支持本地模型向导、已有本地端点和远程 API 三种接入方式。
- 不要求用户安装 PostgreSQL、Redis、Milvus 等外部基础设施。
- 提供清晰任务视图，而不只是聊天窗口。

### 7.2 Agent 能力目标

- 复杂任务在执行前必须形成可验证计划。
- 每个步骤只获得最小充分上下文和有限工具。
- 每个步骤完成后持久化状态、证据和产物。
- 失败必须进入明确的重试、重规划、等待用户或终止状态。
- 重启后可以继续，不重复已提交的副作用。

### 7.3 小模型友好目标

- 减少一次决策可选工具数量。
- 使用结构化输出和 Schema 校验。
- 将复杂问题拆成单目标步骤。
- 将并发交给调度器，不要求模型生成复杂并行调用。
- 保留足够的推理和输出预算，不把上下文填满。
- 提供一次受控格式修复，失败后不猜测执行。

### 7.4 质量目标

以下指标由评测系统持续追踪：

- 工具参数 Schema 首次通过率和修复后通过率。
- 计划合法率、循环依赖率和重规划次数。
- Step 验证通过率和任务最终完成率。
- 崩溃恢复成功率。
- 副作用重复执行次数，目标必须为零。
- 危险操作未授权执行次数，目标必须为零。
- 关键记忆召回率和无关上下文比例。
- 本地模型与 API 模型的延迟、Token、成本和结果差异。

## 8. 产品原则

### 8.1 确定性外壳，概率性内核

模型可以提出方案、选择动作和解释结果；状态迁移、权限、预算、幂等、重试和完成判定由程序控制。

### 8.2 计划优先

简单任务允许使用程序生成的最小计划；复杂任务必须由 Planner 输出结构化计划并通过校验。

### 8.3 证据优先

没有测试结果、文件差异、工具输出或其他证据的步骤不能自动标记完成。

### 8.4 原始数据不可变

事件和原始 Artifact 追加保存；摘要、记忆和索引属于可重建派生数据。

### 8.5 渐进式披露

模型先看到工具和 Skill 的简短索引，只有选中后才获得完整 Schema、说明或参考资料。

### 8.6 失败可见

系统不得用静默降级掩盖失败。评测模式尤其禁止本地模型失败后自动切换 API。

### 8.7 本地优先但不排斥 API

所有核心能力既能运行在本地模型，也能运行在远程 API；两者通过相同契约接入和评测。

## 9. 产品形态

### 9.1 桌面应用

- Windows 作为第一发布平台。
- Wails 提供窗口、菜单、托盘、文件选择和桌面生命周期。
- Vue 3 + TypeScript 提供界面。
- Go Agent Core 编译进应用或以受控子进程运行。

### 9.2 CLI

CLI 用于开发、自动化测试、无界面任务和故障诊断。桌面端与 CLI 必须调用同一核心服务。

### 9.3 模型运行方式

- 托管本地 Runtime：软件管理 llama.cpp 等子进程。
- 已有本地服务：连接用户运行的 vLLM、SGLang、LM Studio、Ollama 等兼容端点。
- 远程 API：连接云端或企业模型网关。

### 9.4 分发方式

- 主程序安装包不强制包含大型模型。
- Runtime 按操作系统和硬件下载。
- 模型作为独立资源包下载、校验、导入和删除。
- 提供包含 Runtime 与模型的企业离线介质。

## 11. MVP 范围

MVP 必须形成一个完整闭环：

1. 用户选择工作区并配置一个模型 Deployment。
2. 系统探测模型能力。
3. 用户创建带验收标准的任务。
4. 系统生成并校验计划。
5. Agent 执行文件和终端工具。
6. 每个步骤保存事件、证据、Artifact 和 Checkpoint。
7. 验证器决定完成、重试或重规划。
8. 程序重启后继续任务。
9. 用户能够查看执行时间线和最终报告。

MVP 暂不包含：

- 递归多 Agent。
- 可视化拖拽工作流。
- 插件市场。
- 企业多租户。
- 全功能浏览器自动化。
- Office、邮件和即时通讯集成。
- 默认依赖外部向量数据库。
- 完全无人监管的长期定时自治。

## 12. 成功标准

项目首个稳定版本不是以功能数量判定，而是需要满足：

- 对基准代码任务可以稳定完成“理解—计划—修改—测试—交付”。
- 相同任务可以无代码改动地切换本地 Qwen 和 API Deployment。
- 任意中间步骤强制终止后，恢复不会重复已完成的副作用。
- 上下文压缩后仍保留目标、约束、计划、证据和下一步。
- 用户能够解释系统当前为何执行、为何等待、为何失败。
- 危险动作必须经过权限系统，无法只靠 Prompt 绕过。
- 所有核心状态均可从 SQLite 和 Artifact 重建。

## 13. 主要风险与应对

| 风险 | 应对策略 |
|---|---|
| 模型工具调用不稳定 | 能力探测、Schema、一次修复、失败暂停、文本 JSON 备用协议 |
| 长任务上下文失真 | 结构化 Checkpoint、事件溯源、Artifact 外置、按步骤检索 |
| 本地模型性能不足 | 硬件检测、量化建议、上下文上限、并发控制、API 备用 Deployment |
| 多 Agent 增加成本和混乱 | 深度限制为一层、结构化报告、确定性调度、严格触发条件 |
| 工具重复副作用 | Write-ahead 记录、幂等键、恢复审计 |
| 权限绕过 | 程序策略判断、规范化路径、审批票据、默认拒绝 |
| 文档领先于实现 | 能力状态标记、契约测试、发布前源码与文档核对 |
| UI 与内核耦合 | Agent Core 独立、事件 API、UI 不保存唯一业务状态 |

## 14. 立项阶段必须产出的基线

- 项目边界与非目标，即本文档。
- 总体架构与数据流。
- Task、Plan、Step、ToolResult、AgentReport、Handoff 契约。
- Qwen3.6-35B-A3B 本地/API 基线评测集。
- 首批工具的权限和风险表。
- MVP 页面流程和状态设计。
- 每个里程碑的退出标准。
