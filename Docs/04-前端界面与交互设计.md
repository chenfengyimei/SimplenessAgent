# SimplenessAgent 前端界面与交互设计

## 1. 设计目标

前端不是聊天消息容器，而是任务运行控制台。它必须帮助用户快速回答：

- 系统现在在做什么？
- 为什么要这样做？
- 哪一步完成、失败或正在等待？
- 使用了什么模型、工具、记忆和权限？
- 产生了哪些文件和证据？
- 用户现在需要决定什么？
- 如果关闭软件，之后能否继续？

## 2. 设计原则

### 2.1 任务优先，聊天辅助

聊天是输入和解释渠道；计划、步骤、证据和 Artifact 才是主视图。

### 2.2 渐进式展示复杂度

普通用户看到目标、进度、审批和结果；开发者可以展开 Token、原始事件、Context Package 和 Provider 响应。

### 2.3 状态必须可区分

不能只显示一个无限旋转的“思考中”。至少区分：

- 正在理解需求。
- 正在侦察项目。
- 正在规划。
- 等待计划审核。
- 正在调用模型。
- 正在执行工具。
- 正在验证。
- 等待用户输入。
- 等待权限审批。
- 正在重规划。
- 已暂停、已取消、已失败、已完成。

### 2.4 风险信息接近动作

审批对话框必须显示实际目标、参数、影响范围和原因，不能只显示“是否允许此操作”。

### 2.5 恢复是正常体验

应用重新打开后，未完成任务显示恢复状态和最后 Checkpoint，而不是伪装成新会话。

```text

├──────────────┬──────────────────────────────────────────┬──────────────────┤
│ 左侧导航      │ 主工作区                                  │ 右侧检查器        │
│              │                                          │                  │
│ + 新建任务    │ 任务标题 / 状态 / 总进度                  │ 当前 Step         │
│ 会话          │ ┌ 对话 | 计划 | 时间线 | 产物 | 上下文 ┐ │ 输入/输出         │

└──────────────┴──────────────────────────────────────────┴──────────────────┘
```

### 左侧导航

- 固定 Workspace 切换。
- Session 与 Task 分组显示。
- Task 图标直接展示运行、等待、失败和完成状态。
- 支持筛选活动任务、需要我处理、最近完成。
- 不在左侧展示过多运行细节。

### 顶部状态栏

- 当前 Workspace。
- 当前 Deployment 和健康状态。
- 本地 Runtime CPU/GPU/内存摘要。
- 当前 Context 使用比例。
- 全局暂停或任务状态。
- 离线、API 限流、模型不可用等系统级警告。

### 右侧检查器

根据选中对象展示 Step、Tool Call、Artifact、Memory 或 Event 详情。主区域保持任务脉络，细节在右侧展开。

## 5. 首次启动向导

### 步骤 1：欢迎与使用模式

提供三种清晰选项：

- 本地模型：软件帮助下载并启动。
- 已有模型服务：填写或自动发现本地端点。
- 云端/API：填写 Endpoint 与凭据。

说明数据边界和网络行为，不预先选择云端。

### 步骤 2：硬件检测

展示：

- 操作系统和架构。
- CPU、内存。
- GPU、显存和驱动。
- 可用磁盘。
- 推荐 Runtime。

结论使用用户可理解的等级：推荐、可运行但较慢、不推荐、无法运行。

### 步骤 3：模型选择

每个模型卡展示：

- 模型和量化名称。
- 下载大小。
- 预计内存/显存需求。
- 当前硬件适配结论。
- 文本、视觉、Tool Calling 和 Thinking 能力。
- 来源、版本和许可证。

### 步骤 4：下载与启动

- 进度、速度、剩余大小和磁盘位置。
- 暂停、继续和取消。
- 下载完成后校验。
- Runtime 启动日志折叠展示。

### 步骤 5：能力探测

逐项展示文本、流式、工具、取消和上下文探测。探测失败不能简单显示“连接失败”，需要显示失败能力和是否仍可继续。

### 步骤 6：首个 Workspace

用户选择目录，系统解释只会在授权范围内操作。可以跳过并进入空白首页。

## 6. 新建任务交互

### 6.1 快速模式

用户直接输入需求。系统自动生成：

- 推断目标。
- 默认 Workspace。
- 建议验收条件。
- 风险和预计复杂度。

用户可以直接开始或展开高级设置。

### 6.2 高级模式

字段包括：

- 目标。
- 非目标。
- 约束。
- 验收条件。
- 允许访问目录。
- 权限策略。
- Deployment。
- 最大时间、Token、步骤和重规划次数。
- 是否允许子 Agent。

### 6.3 澄清交互

只有会实质改变结果时才阻塞询问。问题展示：

- 为什么需要回答。
- 推荐选项。
- 每个选项的影响。
- 是否允许使用默认假设继续。

## 7. 计划页面

### 7.1 展示层级

- 任务目标和验收条件。
- Plan Version 和生成时间。
- 阶段分组。
- Step 状态、依赖、风险、负责人和预计产物。

### 7.2 状态视觉

| 状态 | 表现 |
|---|---|
| Pending | 中性灰色 |
| Ready | 蓝色轮廓，可执行 |
| Running | 蓝色动态指示，但不持续闪烁 |
| Waiting Approval | 黄色锁形提示 |
| Waiting User | 黄色问号提示 |
| Verifying | 紫色检查提示 |
| Completed | 绿色并显示证据数量 |
| Failed | 红色并显示失败分类 |
| Superseded | 删除线或旧版本标记 |
| Skipped | 淡化并显示原因 |

### 7.3 计划审核

用户可以：

- 同意全部计划。
- 编辑目标或约束后重新规划。
- 禁用某一步。
- 降低权限。
- 指定必须人工确认的步骤。

手工编辑计划后重新运行程序校验，不能直接绕过 Schema。

### 7.4 重规划展示

以 Diff 显示：

- 保留步骤。
- 新增步骤。
- 删除或被替代步骤。
- 依赖变化。
- 重规划原因和证据。

## 8. 时间线页面

时间线按事件而非纯消息展示：

- 用户创建任务。
- 完成侦察。
- 生成 Plan v1。
- Step 进入 Ready/Running。
- 模型调用。
- Tool Call、审批和 Tool Result。
- Artifact 创建。
- 验证结果。
- Checkpoint。
- 重规划。
- 完成或失败。

默认折叠底层 Token 事件，开发者模式可展开原始详情。

## 9. 工具执行与审批交互

审批卡必须展示：

- 工具名称和风险等级。
- Agent 为什么需要执行。
- 实际命令或文件操作。
- 规范化后的目标路径。
- 是否有外部网络或副作用。
- 预计超时。
- 与当前 Step 的关系。

审批范围：

- 仅本次。
- 本任务相同参数模式。
- 本 Workspace 本次会话。
- 永久规则，仅对低风险可用。
- 拒绝并告诉 Agent 原因。

批准票据绑定参数哈希；工具参数变化后必须重新审批。

## 10. Artifact 页面

按类型分组：

- 文件修改和补丁。
- 命令日志。
- 测试报告。
- 分析报告。
- AgentReport/Handoff。
- 模型原始调试响应。

功能：

- 文本预览、Diff、行号和搜索。
- 在系统文件管理器中定位。
- 复制稳定引用。
- 查看来源 Step、哈希和验证状态。
- 导出任务交付包。

## 11. 上下文检查器

上下文页面按预算分区展示：

- System Contract。
- TaskSpec 和 Plan。
- 最近消息。
- 检索记忆。
- 项目知识。
- Skill。
- Tool Schema。
- Artifact 摘要。
- 输出与推理预留。

每条检索内容展示：来源、得分、作用域、占用 Token、为何注入。用户可以临时排除或固定某条内容后重新运行 Step。

## 12. 记忆页面

### 列表能力

- 按类型、Workspace、Task、来源、状态和时间筛选。
- 搜索记忆。
- 显示置信度、重要性和最近命中。
- 查看来源 Event/Artifact。

### 用户操作

- 固定。
- 修改。
- 标记不正确并压制。
- 归档。
- 删除或请求忘记。
- 建立替代关系。

自动记忆和用户明确确认的记忆需要有不同视觉标识。

## 13. 模型中心

### Deployment 列表

展示：

- 本地/API 标识。
- 模型名称。
- 健康状态。
- Runtime/Endpoint。
- 量化和上下文。
- 能力探测时间。
- 当前任务数量。

### 能力详情

以矩阵展示：

- Text。
- Streaming。
- Tool Calling。
- Parallel Tools。
- Thinking。
- Preserve Thinking。
- Vision。
- Token Count。
- Cancellation。

能力由探测结果和用户覆盖共同形成，覆盖行为必须醒目标记。

### 本地 Runtime

- 启动、停止、重启。
- 模型切换。
- CPU/GPU 负载。
- Context、并发和内存参数。
- 日志。

## 14. 评测中心

- 选择 Suite、Cases 和 Deployments。
- 明确提示评测模式禁止静默故障转移。
- 显示执行队列和并发。
- 对比成功率、工具合法率、耗时、Token、成本、重规划和恢复。
- 支持打开失败 Case 的完整时间线。
- 对同一 Case 进行结果 Diff。

## 15. 错误和恢复体验

错误页面应提供四层信息：

1. 用户语言：发生了什么。
2. 影响：任务是否还能继续。
3. 建议动作：重试、修改配置、授权、重新规划或查看日志。
4. 技术详情：错误码、Step、Attempt、Deployment、Artifact。

启动时发现未完成任务：

- 展示最后 Checkpoint 时间。
- 展示是否存在执行中的外部进程。
- 提供恢复、保持暂停、终止三个选项。
- 恢复前运行幂等审计。

## 16. 快捷键和可访问性

- 全局命令面板。
- 新建任务、暂停、取消、打开计划、打开审批的快捷键。
- 键盘可操作所有审批和对话。
- 不只依赖颜色区分状态。
- 支持字体缩放、减少动画、深浅主题。
- 中文为首要语言，界面字符串集中管理，预留国际化。

## 17. 前端状态管理原则

- Pinia 只保存视图状态和服务端状态缓存。
- Task 真相来自 Go Core/SQLite。
- 所有命令具有 request ID，避免重复点击。
- 事件包含顺序号，前端断线后按游标补拉。
- 乐观更新只用于无副作用 UI 操作；任务状态等待 Core 确认。
- 页面刷新或窗口重建后可以从快照和事件恢复。

## 18. 前端开发顺序

1. 设计 Token、状态色和基础组件。
2. Mock Event Stream 构建任务时间线。
3. 对接真实 Workspace、Task 和 Event 查询。
4. 完成计划和审批闭环。
5. 完成 Artifact 和诊断。
6. 完成模型向导与 Model Manager。
7. 完成记忆、上下文和评测高级页面。
8. 最后进行动画、主题和视觉精修。
