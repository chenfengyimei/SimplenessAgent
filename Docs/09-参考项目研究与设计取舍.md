# 参考项目研究与设计取舍

## 1. 研究说明

本文基于 2026-08-11 拉取的九个参考项目默认分支，对 README、架构文档、模块结构以及规划、执行、工具、记忆、多 Agent、持久化、安全等关键源码链路进行阅读和交叉验证。

参考原则：

- 学习抽象和工程模式，不复制项目定位。
- README 声明与源码实现分开判断。
- 只吸收能服务于“小模型可靠执行”目标的能力。
- 许可证、依赖和代码复用在实际采用前单独审查。

## 2. uniTerm

来源：[ys-l/uniterm](https://gitee.com/ys-l/uniterm)

### 定位

Go + Wails 的多协议终端和本地桌面工具，内置可以多轮执行 Shell 命令的 Agent。

### 可吸收内容

- Go + Wails + Vue 的桌面软件形态验证。
- 终端 Shell、活动面板和目标会话动态注入。
- Tool Input 在执行前做前端/运行时形状校验。
- 命令、长任务、输出收集、中断和交互输入分成不同工具。
- 技能只把名称和描述放入 System Prompt，正文按需加载。
- 会话分片存储、原子写入和损坏文件隔离。
- 多种审批模式和工具结果大小限制。

### 不照搬内容

- Agent Loop 主要位于前端，不适合作为持久化运行核心。
- 上下文预算与特定模型窗口硬编码。
- 缺少结构化长期记忆和持久化 Plan。
- 风险部分来自模型输入，不能作为最终安全判断。
- 单工具调用规则适合模型，但并行应由调度器实现。

### 在本项目中的落点

- 桌面架构、Model Manager 交互、终端工具拆分、Skill JIT、会话损坏隔离。

## 3. CogitoAgent

来源：[cnt-code/cogito-agent](https://gitee.com/cnt-code/cogito-agent)

### 定位

Electron + TypeScript 的本地 AI 助手，工具范围广，具备原生 Tool Calling 和多 Agent 编排能力。

### 可吸收内容

- 原生 Tool Call、JSON Schema 和调用顺序处理。
- 并行工具结果保持原始调用顺序。
- 最大步骤、Token、成本和取消预算。
- 流式停止、超时、空响应重试和协议修复。
- 上下文压缩时保持 Tool Call/Result 边界。
- 子 Agent 数量、并发、迭代和超时限制。
- 完整运行事件和思考/统计可观察性。

### 不照搬内容

- 功能和工具数量过多会扩大有限模型选择面。
- 记忆仍偏平面 JSON/关键词结构。
- 复杂任务没有强制使用持久化 Plan。
- 子 Agent 返回主 Agent 的摘要可能只是字符串截断，不足以作为语义交接。
- Electron 对本项目期望的轻量本地分发不是首选。

### 在本项目中的落点

- Provider 协议、工具循环、预算、取消、观测和 Agent 生命周期。

## 4. HanFlow

来源：[easy-es/hanflow](https://gitee.com/easy-es/hanflow)

### 定位

基于 Python、LangGraph、YAML DSL 和 Pydantic 的 Agent 工作流框架。

### 可吸收内容

- 声明式 YAML/Schema 作为流程单一来源。
- 静态工作流、动态协调和混合模式的抽象。
- 节点注册表和 Node Executor 边界。
- Scratch、Session、Long-term 三类记忆作用域。
- Skill 与 Tool 白名单。
- Checkpoint、Session Store、Artifact、RAG 和隐私路由接口。
- 动态协调器必须有最大步数的思想。

### 需要警惕

源码阅读中，部分条件路由、循环、并行、子工作流、HITL 和动态 Coordinator 行为仍偏骨架或未完整执行文档语义。因此应学习 DSL、验证和扩展接口，不以其当前实现完整度作为本项目执行内核依据。

### 在本项目中的落点

- Plan Schema、节点注册、静态/动态混合和 Checkpoint 抽象。

## 5. MothX

来源：[startvibecoding/mothx](https://gitee.com/startvibecoding/mothx)

### 定位

Go 编写的本地 Agent/CLI/TUI，支持多 Provider、工具、会话事件、压缩、子 Agent 和工作流。

### 可吸收内容

- Go 单二进制和清晰 Agent API。
- SQLite 会话事件树、稳定 ID、分支和压缩 Checkpoint。
- 固定 System Prompt/Tool Definition 与动态上下文分离。
- 模型特定 Token 估算和请求预算防护。
- 超大 Tool Result 单独压缩或外置。
- 上下文溢出重试、Tool 配对修复和空响应处理。
- 工具执行记录和重放时避免副作用再次执行。
- Context Pressure、Iteration Pressure 和 Stuck Loop 事件。
- 子 Agent Session、Registry、Tool 和 Workspace 隔离。
- 取消、审批和结构化子 Agent 结果。
- 对 Windows 沙箱尚未实现保持真实说明，而不是文档伪装支持。

### 不照搬内容

- Plan 更偏展示，不应作为本项目唯一持久化执行真相。
- 长期记忆较薄。
- 模型生成任意 JavaScript 工作流对有限模型不够稳。
- 已激活 Skill 正文可能占据 System Prompt，应进一步 JIT。

### 在本项目中的落点

- 作为执行内核最主要参考：事件、恢复、幂等、压缩、取消、压力和子 Agent 隔离。

## 6. Ragent

来源：[nageoffer/ragent](https://gitee.com/nageoffer/ragent)

### 定位

Java 模块化单体的生产级 RAG 应用平台，覆盖摄取、检索、问答、模型路由、MCP 和管理后台。

### 可吸收内容

- 问题改写、多问题拆分和历史补全。
- 树形意图、歧义引导和多知识库路由。
- 向量、关键词、图谱、联网等多通道并行召回。
- 通道超时隔离、去重、RRF、Rerank 和 TopK 漏斗。
- 检索预算和完整 Trace。
- 模型能力分层、候选路由、健康状态和故障转移。
- 策略、模板方法、注册表和责任链在 AI 工程中的具体使用。
- 证据引用、Grounding 和结果来源展示。

### 不照搬内容

- 依赖 Spring、关系库、向量库、搜索引擎和多种服务，普通本地用户部署过重。
- 产品核心是 RAG 问答，不是通用任务状态机。
- 会话摘要不能替代本项目结构化 Task Memory。

### 在本项目中的落点

- Context Compiler、混合检索、检索预算、模型路由、证据和可观测性。

## 7. ChubbySkills

来源：[chubbyguan/chubbyskills](https://gitee.com/chubbyguan/chubbyskills)

### 定位

围绕内容获取、转写、加工、知识库和学习流程的 Agent Skills 集合。

### 可吸收内容

- Skill 作为声明式 SOP，而不是普通长 Prompt。
- 原始资料不可变、AI 整理层、临时视图层的知识分层。
- 所有整理内容保留来源。
- Skill 依赖分层和统一 Markdown Frontmatter。
- 先运行确定性脚本，再让模型处理高价值语义步骤。
- 输出契约、质量等级、处理限额和知识健康审计。
- 摄取写入、MCP 只读查询形成闭环。

### 不照搬内容

- 主要是技能内容，不是 Agent Runtime。
- 部分路径和约束偏个人环境。
- 大量静态技能说明需要通过索引和按需加载治理。

### 在本项目中的落点

- Skill 格式、Knowledge 分层、来源追踪、审计和渐进披露。

## 8. Snail-AI

来源：[aizuda/snail-ai](https://gitee.com/aizuda/snail-ai)

### 定位

Spring Boot/Spring AI 的企业级 Agent 管理、RAG、模型、Skill 和 Server-Agent 平台。

### 可吸收内容

- Server 与 Agent Client 通过 gRPC 分离。
- Agent 请求经过有序责任链：初始化、会话、模型、Prompt、MCP、Skill、RAG、Context、LLM。
- 多实例客户端路由和健康管理。
- Model、Agent、RAG、Skill 和资源管理后台。
- 记忆类型、状态、来源、检索调试和上下文预览的产品设计。
- RAG 的向量/BM25、融合、重排和指标。

### 需要区分文档与实现

当前源码中短期记忆已经落地；长期记忆的大量架构说明和管理对象并未形成与文档完全对应的执行链。多 Agent 协作和 DAG 工作流在路线图中仍属于规划能力。因此这些内容可作为产品和数据设计参考，不能视为已验证实现直接复制。

### 在本项目中的落点

- Handler Pipeline、管理界面、分布式扩展预留、记忆类型和检索调试 UI。

## 9. QRClaw

来源：[fu-qingrong/qrclaw](https://gitee.com/fu-qingrong/qrclaw)

### 定位

Python 本地 Agent，具有 ReAct、复杂任务路由、DAG PlanExecutor、Replanner、Wiki Memory 和 Skill。

### 可吸收内容

- Router 将简单任务和复杂计划任务分流。
- Pydantic 结构化 Plan、依赖、重试和 DAG 分层执行。
- 每层执行完成后根据真实 StepReport 重规划。
- 子 Agent 使用隔离 ContextManager。
- 并行子任务只共享必要结果摘要。
- Wiki 页面、索引、日志和后台记忆提取。
- Skill 名称描述常驻，正文通过工具按需加载。
- 上下文达到 Token 阈值时摘要并保留最近内容。

### 不照搬内容

- Plan 主要在内存中，不能承担崩溃恢复。
- 重规划需要更严格的全局上限和版本控制。
- Wiki 检索和记忆治理较简单，来源、冲突和重复仍需增强。
- 缺少独立 Verification Gate。
- 沙箱失败后退回本地执行属于 fail-open，本项目不能采用。

### 在本项目中的落点

- Planner、DAG Scheduler、StepReport、局部重规划、Context 隔离和 Skill JIT。

## 10. iforgeAI

来源：[jordium/iforgeai](https://gitee.com/jordium/iforgeai)

### 定位

由多个专业角色、阶段文件和 Prompt 组成的软件开发流程工具包。

### 可吸收内容

- 需求、架构、数据库、UI、任务拆解、接口、开发、审查、QA、DevOps 的角色边界。
- 每阶段明确输入、输出和禁止事项。
- 通过 `.ai/context`、`.ai/records`、`.ai/reports` 等持久化 Artifact 交接。
- 人工审核门和退回机制。
- 文件级开发计划、顺序和集成风险。
- 角色通过交付物接力，而不是共享无限聊天历史。

### 不照搬内容

- 主要依靠 Prompt 约定，缺少强制执行引擎。
- 文件存在不能证明阶段完整或正确。
- 固定长流程不适合所有日常任务。
- Artifact 缺少统一 Schema、版本、哈希和自动验证。

### 在本项目中的落点

- Agent Role、Artifact Handoff、Human Gate、文件级计划和验证清单。

## 11. 综合吸收矩阵

| 本项目能力 | 主要参考 |
|---|---|
| Go 执行内核和桌面形态 | MothX、uniTerm |
| Tool Calling、取消、预算和协议修复 | CogitoAgent、MothX、uniTerm |
| Planner、DAG 和 Replanner | QRClaw、HanFlow |
| 持久化交接和角色边界 | iforgeAI、MothX |
| 记忆模型和管理体验 | Snail-AI、ChubbySkills |
| 混合检索、RRF、Rerank | Ragent、Snail-AI |
| Skill 渐进式加载 | ChubbySkills、QRClaw、uniTerm |
| 管理控制台和 Trace | Ragent、Snail-AI、CogitoAgent |
| 本地模型与多 Provider | MothX、CogitoAgent、uniTerm |
| 声明式工作流和扩展接口 | HanFlow |

## 12. 明确不采用的模式

- 把全部工具 Schema 永久塞进 System Prompt。
- 把一段会话摘要作为唯一长期记忆。
- 让模型输出任意代码作为核心工作流 DSL。
- 由模型自行决定权限和风险。
- 沙箱失败后静默在宿主机执行。
- 只凭文件存在或 Agent 自述判定完成。
- 子 Agent 只返回定长字符串截断摘要。
- 复杂任务 Plan 不持久化。
- README 先宣称支持、源码和测试以后再补。

## 13. 研究结论

没有一个参考项目同时满足本项目的全部目标。最合理的路线是：

- 用 MothX/CogitoAgent 的执行可靠性作为地基。
- 用 QRClaw 的规划循环和 iforgeAI 的持久化交付物解决复杂任务。
- 用 Ragent/Snail-AI 的检索工程和 ChubbySkills 的知识治理解决上下文。
- 用 uniTerm 的桌面交互和本地模型体验完成产品化。
- 用 HanFlow 的声明式抽象约束未来扩展，但重新实现并充分测试执行语义。
